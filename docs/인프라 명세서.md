# 인프라 명세서

## 1. 목적

Frontend, Spring Backend, AI Server, Backtesting Worker, Market Data Collector 및 Database를 Docker 기반으로 배포하고 운영한다.

연산 시간이 긴 백테스트는 일반 API 요청과 분리하고, `Message Queue + 다중 Worker` 구조를 적용하여 여러 백테스트 요청을 병렬 처리한다.

또한 Worker Replica 수를 단계적으로 증가시키며 수평 확장에 따른 성능 변화를 측정한다.

---

## 2. 전체 구조

```
                     Client
                       ↓
                     Nginx
                       ↓
                Spring Backend
                       ↓
              Backtest Job 생성
                       ↓
                   RabbitMQ
                       ↓
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
   Worker #1       Worker #2      Worker #N
        │              │              │
        └──────────────┼──────────────┘
                       ↓
                   Shared DB
```

추가 서비스:

```
Frontend
AI Server
Market Data Collector
```

### 역할 분리

**Spring Backend**

- 백테스트 요청 접수
- Backtest Job 생성
- 상태 조회
- 결과 조회

**RabbitMQ**

- Backtest Job Queue 관리
- Worker 간 작업 분배

**Backtest Worker**

- 실제 백테스트 연산 수행

## 3. Docker 구성

서비스를 독립적인 Container로 실행한다.

```
nginx
frontend
backend
ai-server
backtest-worker
market-data-collector
rabbitmq
database
```

Backtest Worker는 동일한 Docker Image를 사용하며 Replica 수만 변경할 수 있도록 한다.

예:

```bash
docker compose up -d --scale backtest-worker=4
```

Worker Scale-out을 위해 Backtest Worker에는 고정된 `container_name`을 사용하지 않는다.

---

## 4. Queue 기반 백테스트 처리

사용자가 백테스트를 요청하면 즉시 Job을 생성하여 Queue에 등록한다.

```
Backtest Request
       ↓
DB : QUEUED
       ↓
RabbitMQ
       ↓
사용 가능한 Worker가 Job 수신
       ↓
DB : RUNNING
       ↓
Backtest 실행
       ↓
DB : COMPLETED / FAILED
```

Worker는 작업을 정상 완료한 후 메시지를 ACK한다.

작업 중 Worker가 비정상 종료되면 완료되지 않은 Job을 다른 Worker가 다시 처리할 수 있도록 구성한다.

Job 상태와 결과는 Worker 내부 메모리가 아닌 공용 저장소에서 관리한다.

---

## 5. Worker 수평 확장

동일한 Backtest Worker를 여러 Container Replica로 실행한다.

```
Worker 1
   ↓
Worker 2
   ↓
Worker 4
   ↓
Worker 8
```

모든 Worker는 동일한:

- Docker Image
- RabbitMQ Queue
- Market Data
- Result DB

를 사용한다.

따라서 Worker 수를 변경하기 위해 애플리케이션 코드를 수정하지 않아도 되는 구조를 목표로 한다.

## 6. 성능 테스트

### 기본 테스트 조건

모든 테스트에서 입력 조건을 동일하게 유지한다.

예:

```
동일 StrategyVersion
동일 MarketDataVersion
1시간봉
동일 백테스트 기간
동일 초기 투자금
동일 Job 개수
```

예를 들어 동시 Backtest Job 20개를 요청하고 Worker 수만 변경한다.

### 테스트 구성

```
Worker 1
Worker 2
Worker 4
Worker 8
```

### 측정 지표

| 지표 | 내용 |
| --- | --- |
| Makespan | 전체 Job 완료까지 걸린 시간 |
| Throughput | 단위 시간당 완료된 Job 수 |
| Queue Wait Time | Job 생성부터 Worker 실행까지 시간 |
| Execution Time | 개별 백테스트 실행시간 |
| P95 Completion Time | 상위 지연 Job 포함 완료시간 |
| CPU Usage | EC2 CPU 사용률 |
| Memory Usage | EC2 메모리 사용량 |
| DB I/O | DB 병목 확인 |
| DB Connection | 동시 Worker 증가에 따른 Connection 변화 |

동일 테스트를 여러 번 반복하여 평균 또는 중앙값으로 비교한다.

## 7. 성능 실험 목표

Worker를 많이 띄우는 것 자체가 목적이 아니라 **어느 시점까지 Scale-out 효과가 발생하는지 확인하는 것**을 목표로 한다.

```
Worker 증가
      ↓
병렬 처리량 증가
      ↓
Queue 대기시간 감소
      ↓
CPU / Memory / DB 부하 증가
      ↓
성능 증가폭 감소
      ↓
단일 EC2 기준 적정 Worker 수 확인
```

단일 EC2 안에서 수행하므로 실제 물리 서버의 수평 확장이 아니라 **동일 서비스의 Container Replica 확장에 따른 성능 변화를 검증하는 실험**으로 정의한다.

## 8. API Load Balancing

Worker 확장과 API 서버 확장은 별도의 실험으로 진행한다.

기본 구조는 Backend 1개로 시작하고, Worker 성능 테스트 이후 필요하면 Backend를 2개 Replica로 구성한다.

```
                   Nginx
                 /       \
                ↓         ↓
          Backend #1   Backend #2
                \         /
                 RabbitMQ
```

Nginx가 HTTP 요청을 두 Backend Instance에 분산한다.

### 검증 목적

- Stateless API 구성
- HTTP Load Balancing 경험
- Backend Instance 장애 대응

백테스트 연산 성능 자체는 Worker 수를 기준으로 평가한다.

---

## 9. 장애 테스트

### Worker 장애

다중 Worker 실행 중 하나를 강제로 종료한다.

```
Worker #1 DOWN

Worker #2 정상
Worker #3 정상
```

확인 사항:

- 다른 Worker가 새로운 Job을 계속 처리하는가
- 처리 중이던 미완료 Job이 재처리되는가
- Job 상태가 정상적으로 관리되는가

### Backend 장애

Backend를 2개 Replica로 운영할 경우 하나를 종료하고 Nginx가 정상 Instance로 요청을 전달하는지 확인한다.

## 10. Market Data 연동

Backtest Worker는 백테스트 실행 중 거래소 API를 직접 호출하지 않는다.

```
Upbit API
    ↓
Market Data Collector
    ↓
Historical Market DB
    ↓
Backtest Worker
```

이를 통해:

- 거래소 API Rate Limit의 영향 감소
- 여러 Worker가 동일한 데이터 사용
- 백테스트 결과 재현성 확보

를 목표로 한다.

Market Data Collector의 데이터 수집 로직이 별도 담당 영역인 경우 인프라에서는 배포 및 실행 상태 관리만 담당한다.

## 14. 핵심 목표

> 백테스트 연산을 Spring Backend와 분리하고 RabbitMQ 기반 Worker 구조로 구성한다. 동일한 Backtest Worker를 여러 Container Replica로 확장하면서 처리량, 대기시간 및 시스템 자원 사용량의 변화를 측정하여 단일 EC2 환경에서 수평 확장의 효과와 한계를 확인한다.
