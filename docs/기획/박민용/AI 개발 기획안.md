# AI 개발 기획안

> 팀 공유용 요약이다. 정본은 `ai/docs/PLAN.md`(구현 계획)와 `ai/docs/TASKS.md`(작업 분해)이고, 진행 상태의 정본은 Jira 에픽 [S15P21A107-12](https://ssafy.atlassian.net/browse/S15P21A107-12)다.

## 1. 목표와 범위

**목표** — Spring 백엔드가 HTTP로 호출하면, 사용자의 자연어 전략 설명을 검증된 전략 DSL(JSON)로 변환해 돌려주는 FastAPI 서버를 만든다.

**범위** — 역할 1(자연어 → DSL)까지. 역할 2(견고성 점수 추론)는 이번 범위 밖이되, 라우터와 서비스 계층을 나중에 모듈만 추가하면 되도록 나눠 둔다.

**인원 / 기간** — 1명 / 5주.

**기술 스택** — Python 3.11, FastAPI, Pydantic v2, `openai` SDK(SSAFY GMS 게이트웨이 경유), pytest.

---

## 2. 설계 원칙

이 다섯 가지가 나머지 결정을 대부분 규정한다.

**① DSL 스펙은 `app/core/schema.py` 한 곳에만 정의한다.**
라우터·서비스·테스트·프롬프트 어디에도 필드명이나 허용값을 다시 적지 않는다. 프롬프트에 들어갈 스펙 문구조차 schema에서 JSON Schema를 뽑아 주입한다. 스펙이 교체될 때 수정 대상은 `schema.py`와 프롬프트 `.txt` 두 종류뿐이어야 한다.

**② API 키는 환경변수로만 읽는다.**
`app/core/config.py`가 유일한 진입점이다. 다른 파일은 `os.environ`을 직접 만지지 않는다. 필수값이 없으면 앱 기동 단계에서 죽는다 — 첫 요청에서 죽으면 안 된다.

**③ 프롬프트는 코드가 아니다.**
`app/prompts/*.txt`로 분리해 프롬프트 수정에 코드 배포가 딸려오지 않게 한다.

**④ 검증 실패 시 오류를 프롬프트에 붙여 최대 2회 재시도한다.**
요청당 LLM 호출은 최대 3회다.

**⑤ 외부 의존은 인터페이스 뒤에 숨긴다.**
`llm_client`를 교체 가능하게 두어 테스트가 네트워크 없이 돈다.

## 3. 선행 개발 원칙

전략 도메인 명세와 ERD가 아직 없는 상태에서 먼저 착수하기 때문에, 다음 규칙을 세워 두었다.

| 원칙 | 내용 |
| --- | --- |
| 무상태 유지 | AI 서버는 DB에 붙지 않는다. 필요한 데이터는 요청 본문으로 받는다 |
| 결정 권한 구분 | 도메인 스펙은 전략팀 소관, 서버 구조·계약 형태는 AI 파트 소관 |
| 우리 계약은 임시안 | 명세가 도착하면 교체된다는 전제로 만든다 |
| 뒤집힐 것을 전제 | 뒤집혔을 때 수정 범위가 두 파일로 끝나는 구조를 먼저 만든다 |
| 협의 시점 표시 | 명세 도착 시 무엇을 갈아끼울지 미리 표시해 둔다 (Phase 2) |

이 원칙 때문에 **작업 순서를 뒤집었다.** 스키마(Epic B)가 임계 경로의 첫머리인데 도메인 결정이 안 끝나서, 명세와 무관한 인프라 구간(Epic A·C·F)을 먼저 한다.

---

## 4. Phase 구성

### Phase 1 — 명세 독립 인프라 (1~2주차)

명세가 없어도 만들 수 있는 것부터 만든다.

| Epic | 내용 | 기간 |
| --- | --- | --- |
| A | 기반 — 패키지 골격, 설정, 헬스체크 | 2일 |
| C | 오류 처리와 로깅 — 예외 계층, 핸들러, 요청 ID | 1.5일 |
| F | LLM 클라이언트 — 게이트웨이 호출, 예외 번역 | 1.5일 |
| B′ | **임시** 스키마 — 명세 도착 시 교체 대상 | 1일 |
| D | 검증기 — 파싱, 스키마 검증, 오류 문구 생성 | 2일 |
| E | 프롬프트 — 시스템·사용자·재시도 템플릿, 빌더 | 2일 |
| G | 오케스트레이션 — 재시도 루프, `changes` 계산 | 2일 |
| H | API 연결 — 엔드포인트, 의존성 주입 | 1.5일 |
| J | 자연어 입력 수집 (병렬 가능) | 1일 |

### Phase 2 — 명세 교체 (명세 도착 직후, 2~3일)

전략 도메인 명세가 오면 `schema.py`와 프롬프트 `.txt`를 갈아끼운다. **이때 다른 파일이 수정되면 원칙 ①이 깨진 것이므로, 어디서 필드명이 샜는지 찾는다.**

### Phase 3 — 튜닝·통합 (3~5주차)

골든 케이스로 프롬프트를 다듬고, Spring과 계약을 맞추고, 배포 설정을 정리한다.

## 5. 주차 배분

| 주차 | 내용 |
| --- | --- |
| 1주차 | 기반, 설정, 오류 처리, LLM 클라이언트 |
| 2주차 | 임시 스키마, 검증기, 프롬프트 |
| 3주차 | 오케스트레이션, API 연결 |
| 4주차 | 프롬프트 튜닝 (골든 케이스 회귀) |
| 5주차 | Spring 통합, 정리, 배포 + 여유 |

---

## 6. 테스트 전략

| 계층 | 대상 | 방식 |
| --- | --- | --- |
| 스키마 | `core/schema.py` | 순수 단위 테스트, 네트워크 없음 |
| 검증기 | `services/validator.py` | 고정된 LLM 응답 문자열 입력 |
| 프롬프트 빌더 | `services/prompt_builder.py` | 자리표시자 치환 결과 확인 |
| 오케스트레이션 | `services/translator.py` | 가짜 `llm_client` 주입 |
| API | `api/v1/strategy.py` | `TestClient` + 의존성 오버라이드 |

**실제 LLM을 치는 테스트는 기본 스위트에 넣지 않는다.** `live` 표시를 달아 수동 실행으로 분리한다. CI가 과금되고 느려지고 불안정해지는 걸 막는다.

**골든 케이스**는 자연어 입력 10~15개와 기대 DSL을 쌓아 두고 프롬프트를 고칠 때마다 수동 실행한다. 완전 일치 대신 "검증을 통과하는가 + 핵심 필드 몇 개가 기대와 맞는가"로 판정한다. 완전 일치를 요구하면 프롬프트를 손댈 때마다 전부 깨진다.

커버리지 목표는 `core/`와 `services/` 라인 85% 이상. `llm_client`의 실제 HTTP 경로는 제외한다.

## 7. 위험 요소

| 위험 | 대응 |
| --- | --- |
| **DSL 스펙 교체** | 수정 범위가 `schema.py` + 프롬프트로 끝나는지 Epic E·H 끝에서 각각 점검 |
| **프롬프트 튜닝 시간 초과** | 4주차에 3일을 잡았지만 더 걸리기 쉽다. 5주차 여유분을 여기 쓴다 |
| **LLM 응답 지연** | 재시도로 대기 시간이 최대 세 배. Spring 타임아웃을 그보다 길게 맞춘다 |
| **역할 2 유입** | 이번 범위는 역할 1까지. LightGBM 파일을 미리 만들지 않는다 |
| **전략팀 명세 지연** | Phase 1이 명세와 무관하도록 순서를 짜 뒀다. 임시 스키마로 전 구간을 먼저 완성한다 |
