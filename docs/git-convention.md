# S15P21A107 작업 컨벤션

> 적용 프로젝트: `S15P21A107` 암호화폐 모의투자·전략 플랫폼
> 협업 도구: GitLab · Jira

## 1. Jira 작업 컨벤션

### 1.1 작업 제목

Jira 작업 제목은 다음 형식을 사용한다.

~~~text
[영역] 대상과 작업 내용
~~~

영역은 `FE`, `BE`, `INGEST`, `AI`, `INFRA`, `COMMON` 중 하나를 사용한다.

- `FE`: Frontend 화면, 차트, 전략 구성 UI
- `BE`: API, 전략, 백테스트, 모의투자 도메인
- `INGEST`: Upbit 데이터 수집·적재·보정
- `AI`: 전략 DSL 변환 및 AI 기능
- `INFRA`: 인프라 및 운영 설정
- 공통 문서는 `COMMON` 영역을 사용한다.
- `COMMON`: 여러 영역에서 함께 사용하는 공통 설정·정책

예시:

~~~text
[BE] 백테스트·모의투자 ERD 상세 설계
[INGEST] Upbit 1시간봉 수집 및 저장
[AI] 자연어 전략 DSL 변환 검증
[INFRA] Kafka·Redis·PostgreSQL 개발 환경 구성
[COMMON] 프로젝트 작업 컨벤션 작성
~~~

작성 규칙:

- Jira 프로젝트 키는 제목에 작성하지 않는다.
- 제목만 보고 대상과 작업 결과를 알 수 있게 작성한다.
- 하나의 Jira 작업에는 하나의 결과물을 명시한다.
- 전체 작업은 Story 또는 Task로 만들고 세부 작업은 Sub-task로 분리한다.
- 독립된 결과물은 별도 Jira 작업으로 분리한다.

### 1.2 작업 내용

Jira 설명은 다음 최소 구조를 사용한다.

~~~markdown
## 목적

작업의 목적을 한두 문장으로 작성합니다.

## 작업 내용

- 수행할 작업을 작성합니다.
- 필요한 경우 변경 대상이나 범위를 함께 작성합니다.

## 완료 조건

- [ ] 작업 결과물이 작성되어 있다.
- [ ] 관련 문서 또는 명세가 반영되어 있다.
~~~

제외 범위, 참고 자료, 의존 작업은 필요한 경우에만 추가한다. Jira 이슈 키는 원본 대문자와 하이픈을 유지한다.

## 2. 브랜치명 컨벤션

모든 작업 브랜치는 다음 형식을 사용한다.

~~~text
feat/<jira-key>
~~~

예시: `feat/S15P21A107-33`

작성 규칙:

- 브랜치 접두사는 항상 `feat`를 사용한다.
- 브랜치명에 Jira 이슈 키를 반드시 포함한다.
- 작업 설명, 영역, 별도 slug는 브랜치명에 작성하지 않는다.
- 하나의 작업 브랜치는 하나의 Jira 작업만 처리한다.

## 3. 커밋 메시지 컨벤션

커밋 메시지는 다음 형식을 사용한다.

~~~text
<type>: <한국어 작업 내용>
~~~

예시:

~~~text
feat: 백테스트 실행 API 구현
fix: 빈 캔들 구간 처리 오류 수정
refactor: 체결 계산 로직 분리
docs: 백테스트 모의투자 ERD 상세 설계
~~~

작성 규칙:

- Type은 영문 소문자로 작성한다.
- 작업 내용은 한국어로 작성한다.
- Jira 키는 커밋 메시지에 직접 작성하지 않는다.
- 제목 끝에 마침표를 붙이지 않는다.
- 하나의 커밋에는 하나의 논리적인 변경만 담는다.
- `수정`, `작업`, `완료`처럼 의미가 불명확한 표현만 사용하지 않는다.

Git Hook을 사용하는 경우 현재 브랜치명에서 Jira 키를 추출해 커밋 메시지 끝에 자동으로 추가할 수 있다. Hook이 적용되지 않은 환경에서도 Jira 키를 수동으로 추가하지 않으며, Jira 연결은 브랜치명과 MR 제목으로 관리한다.

## 4. Merge Request 컨벤션

### 4.1 MR 제목

~~~text
[<PART>] <type>: <한국어 작업 내용>-<jira-key>
~~~

예시:

~~~text
[BE] feat: 백테스트 실행 API 구현-S15P21A107-40
[BE] docs: 백테스트 모의투자 ERD 상세 설계-S15P21A107-33
[INGEST] feat: Upbit 캔들 수집 구현-S15P21A107-41
[AI] feat: 전략 DSL 변환 검증 구현-S15P21A107-42
[INFRA] chore: 로컬 Kafka 환경 구성-S15P21A107-43
[COMMON] docs: 프로젝트 작업 컨벤션 작성-S15P21A107-44
~~~

작성 규칙:

- 영역은 대문자로 작성한다.
- Type은 영문 소문자로 작성한다.
- 작업 설명은 한국어로 작성한다.
- Jira 키는 제목 맨 끝에 직접 작성한다.
- 브랜치의 Jira 키와 MR 제목의 Jira 키는 일치해야 한다.
- 작업 설명과 Jira 키는 하이픈으로 구분한다.
- 제목 끝에 마침표를 붙이지 않는다.

### 4.2 MR 본문

MR 본문은 다음 최소 구조를 사용한다.

~~~markdown
## Jira

- [S15P21A107-00](https://ssafy.atlassian.net/browse/S15P21A107-00)

## 변경 사항

- 변경 내용을 작성합니다.

## 확인 사항

- [ ] 변경 내용을 확인했습니다.
- [ ] 관련 문서 또는 명세를 반영했습니다.
~~~

MR의 Target branch는 `develop`으로 설정한다. Reviewer를 지정하고, 필요한 경우 관련 Jira 작업이나 MR을 변경 사항에 함께 작성한다.

## 5. 백엔드 확장 작업의 가상 이슈 운영

이 절은 사용자가 요청한 개인 백엔드 확장 작업에 적용한다. 실제 Jira·GitHub 이슈를 생성하지 않고 [가상 이슈 목록](backend-extension-issues.md)으로 범위와 완료 조건을 관리한다. 기존 팀 작업에는 앞 절의 Jira·MR 규칙을 그대로 적용한다.

### 5.1 이슈와 브랜치

- 가상 이슈 ID는 `AQ-BE-000`, `AQ-BE-001`처럼 부여한다. 외부 서비스의 실제 이슈 번호가 아니다.
- 이 작업에 한해 Jira 키 대신 가상 이슈 ID를 사용해 `feat/AQ-BE-001` 형태로 브랜치를 만든다. 한 브랜치에는 하나의 이슈만 처리한다.
- 첫 브랜치는 현재 기준 커밋에서 시작하고, 다음 이슈는 직전 이슈의 완료 기록 커밋까지 포함한 HEAD에서 새 브랜치를 만든다. 이슈마다 기준 커밋을 기록해 그 이슈에서 추가된 커밋을 구분한다.
- 원격 저장소의 이슈 브랜치에 푸시한다. 기본 브랜치 병합이나 실제 이슈·PR 생성은 이 흐름에 포함하지 않는다.

### 5.2 최소 커밋 단위

- 하나의 커밋은 독립적으로 설명하고 검증할 수 있는 논리적 변경 하나다. 단순히 수정한 파일 수나 안내한 단계 수로 나누지 않는다.
- 예를 들어 차트 테스트의 Bean 등록과 해당 조회 계약에 맞는 fixture 수정은 함께 검증돼야 하므로 하나의 수정 커밋으로 묶는다.
- 각 커밋 단위가 끝나면 관련 검증을 확인하고 즉시 로컬 커밋한다. 아직 검증하지 않은 변경과 다른 작업의 변경을 함께 넣지 않는다.
- 사용자가 코드를 수정·실행하고 Codex가 안내하는 현재 방식을 유지한다. Codex는 실제 변경과 검증 결과를 확인한 뒤 커밋·푸시한다. 기존 결과를 사용하는 경우 검증 당시 소스와 현재 소스가 같은지 확인한다.
- 커밋 메시지는 기존 `<type>: <한국어 작업 내용>` 형식을 따른다. 가상 이슈 연결은 브랜치와 완료 기록에서 관리한다.
- 변경 파일을 명시적으로 스테이징하고 staged diff를 확인한다. 생성물, 비밀값, 관련 없는 사용자 변경은 커밋하지 않는다.

### 5.3 이슈 완료와 기록 시점

1. 이슈의 최소 커밋 단위를 하나씩 완료·검증·커밋한다. 각 안내에는 현재 이슈 ID, 커밋 단위, 완료 조건을 표시한다.
2. 이슈 전체의 완료 조건과 필요한 빌드·테스트를 확인한다.
3. 해당 이슈 브랜치의 작업 커밋들을 `origin`에 푸시하고 성공 여부를 확인한다. 강제 푸시는 사용하지 않는다.
4. 작업 커밋 푸시가 성공한 뒤 [작업·검증 기록](backend-extension-log.md)에 이슈 단위 완료 기록을 작성한다. 목적·원인·개인 기여·수정·검증·한계·포트폴리오 설명과 함께 기준 커밋, 작업 커밋 목록, 원격 브랜치, 푸시한 작업 HEAD, 증빙 위치를 남긴다.
5. 완료 기록과 이슈 상태 변경을 문서 커밋 하나로 묶고 같은 브랜치에 추가 푸시한다. 기록 커밋 자체의 해시는 최종 보고에서 알린다. 기록 안에 자신의 최종 해시를 넣기 위한 재커밋은 하지 않는다.
6. 다음 이슈 브랜치를 시작한다. 푸시가 실패하면 원인을 해결하기 전까지 푸시 완료로 기록하지 않는다.

진행 중에는 이슈 목록의 커밋 체크리스트와 필요한 검증 증빙만 유지한다. 테스트 보고서가 덮어써지기 전에 원본을 저장소 밖에 보관하되, 세부 완료 기록은 매 안내 단계마다 추가하지 않고 위의 이슈 완료 시점에 작성한다. 운영 방식 전환 전에 작성한 기록은 당시의 이력으로 보존한다.
