# ADR-0016. 대회 데이터는 Flyway 마이그레이션으로 넣는다

- 상태: 채택
- 날짜: 2026-09-16
- 관련: ADR-0006, ADR-0010, ADR-0014
- 대체: ADR-0014의 적재 결정(6번)

## 배경

- ADR-0014는 로컬 도구가 생성기 출력을 `contest` 테이블에 직접 넣기로 했다. 그러면 환경마다 사람이 도구를 돌려야 하고, 대회 데이터가 없는 환경이 생긴다.
- 회차 데이터는 대회를 열 때 한 번 만들어 마감까지 고정한다 (ADR-0010). 한 번 적용하고 바꾸지 않는다는 점이 마이그레이션과 같다.
- 1회차 데이터는 4벌 × 10종목이고, 1시간봉 120,960행, 4시간봉·일봉까지 합치면 156,240행이다.

## 결정

1. 회차 데이터를 마이그레이션 한 장으로 만든다. `ai/scripts/contest_sim/export_seed_sql.py`가 생성기 출력에서 SQL을 만들고, 사람이 손으로 고치지 않는다.
2. SQL에는 1시간봉만 넣고 4시간봉·일봉은 마이그레이션 안에서 집계한다 (ADR-0005 롤업 규칙). 파일이 30MB에서 14MB로 줄고, 집계가 생성기와 어긋날 수 없다.
3. 종목은 `asset_id`가 아니라 마켓 코드로 `reference.asset`과 조인해 붙인다. 환경마다 `asset_id`가 달라도 같은 파일이 돈다.
4. 대회 종목이 없는 환경에서는 그 종목을 `reference.asset`에 넣는다. 이미 있으면 그대로 둔다. 수집 대상으로는 등록하지 않는다.
5. 회차의 종목 수가 모자라면 마이그레이션이 예외를 던져 배포를 멈춘다. 종목이 빠진 채로 대회가 열리지 않게 한다.
6. 다음 회차는 새 마이그레이션 한 장을 더한다. 이미 적용한 파일은 고치지 않는다.

## 검토한 대안

- **로컬 적재 도구 (ADR-0014 결정 6).** 환경마다 사람이 돌려야 하고, 운영에 넣으려면 DB 접속 정보를 손에 들어야 한다.
- **gzip CSV를 리소스에 넣고 Java 마이그레이션에서 COPY.** 적재는 더 빠르지만(수 초) 압축 파일 5.8MB가 저장소에 들어가고 마이그레이션 코드가 생긴다. SQL 텍스트는 14MB지만 git 압축 뒤에는 더 작고, 무엇이 들어가는지 파일에서 바로 읽힌다.
- **적재 API.** 대회 데이터를 운영에서 만들지 않기로 해서(2026-09-15 범위 정리) 받을 곳이 없다.

## 결과

- 로컬 빈 DB에서 V21 적용에 7.1초 걸렸다(V20은 0.07초). 1시간봉 120,960행을 500행씩 나눈 INSERT와 집계 두 번이다.
- 1회차 데이터는 생성기 시드 20260915, 원본 구간 2019-10-07 ~ 2021-10-04, 10종목이다. 데이터셋 ID는 회차 UUID에서 uuid5로 파생해 파일을 다시 만들어도 같다.
- 회차의 제출 기간이 파일에 박혀 있다. 로컬에서 기간을 당겨 시험하려면 DB에서 직접 바꾼다. 운영에서 기간을 바꾸려면 새 마이그레이션이 필요하다.
- 1회차 데이터로 제출 → 마감 → 채점 → 결과를 로컬에서 한 번 돌렸다(2026-09-16, S15P21A107-225). 데이터셋 4벌 백테스트가 모두 `COMPLETED` 로 끝나고 결과가 나왔다.
- 생성된 SQL은 `ai/tests/test_contest_export_seed.py` 가 본다. DB 적용은 백엔드 `ContestRoundSeedMigrationTest` 가 본다.
- 대회 데이터를 바꾸려면 새 회차를 새 마이그레이션으로 넣는다. 같은 회차를 고치는 방법은 두지 않았다.
