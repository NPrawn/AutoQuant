# ADR-0007. 배치를 만들기 전에 로컬에서 대회를 시뮬레이션한다

- 상태: 채택
- 날짜: 2026-09-14
- 관련: ADR-0003, ADR-0006, ADR-0011, ADR-0012

## 배경

- develop에는 대회 기능이 없다. 백엔드에 contest 코드가 없고, 프론트 대회 화면(`ContestListPage` 등)은 API를 호출하지 않는다.
- ADR-0006의 배치·테이블·provider를 먼저 만들었는데 채점식(ADR-0003)이나 조작 방식(ADR-0011)이 틀린 것으로 드러나면 여러 모듈을 되돌려야 한다.
- 조작 방식의 검증(ADR-0012)도 이 시뮬레이션 환경에서 한다.

## 결정

백엔드 코드를 바꾸지 않고, 로컬에서 기존 백테스트 API로 대회를 한 번 시뮬레이션한다.

1. Docker로 Postgres·RabbitMQ·Redis를 띄우고 develop 기준 Spring을 로컬에서 기동한다.
2. `reference.asset`에 테스트 종목을 넣는다.
3. 데이터셋마다 `market_data.minute_candle`을 비우고 1시간봉·4시간봉·일봉을 직접 넣는다. 롤업 트리거는 1분봉 insert에만 걸려 있어 동작하지 않는다.
4. 참가 전략 약 10개를 `POST /strategies`로 만들고, 데이터셋마다 `POST /backtests`로 돌려 `result`와 `equity`를 모은다. `marketDataVersion`에 데이터셋 이름을 넣어 결과를 구분한다.
5. 채점 스크립트로 ADR-0002·0003의 점수와 순위를 낸다.

데이터셋은 5벌이다: REAL(실제, 비교 기준), PERTURBED(변조), BULL, BEAR, SIDEWAYS.

## 검토한 대안

- **contest 테이블과 대회용 provider까지 만들어 적재한다.** 저장 설계까지 검증되지만 migration, provider, 선택 경로 모두 백엔드 작업이라 한 번 시험하기에는 크다.
- **엔진 없이 Python으로 간이 백테스트를 한다.** 가장 빠르지만 체결 시점, 수수료, 슬리피지, 캔들 부족 종목 제외 규칙이 엔진과 달라 결과를 믿기 어렵다.

## 결과

- ADR-0006의 테이블과 provider 설계는 이 시뮬레이션으로 검증되지 않는다.
- 로그인은 SSAFY OAuth뿐이지만 백엔드 코드를 바꾸지 않고 호출할 수 있다. `JwtAuthenticationFilter`는 `Authorization: Bearer` 헤더를 받고, 토큰은 `JWT_SECRET`으로 서명한 HS256 JWT다 (발급자 `JWT_ISSUER`, 기본값 `a107`, subject는 member UUID). 로컬에서 `JWT_SECRET`을 정해 기동하고 `account.member` 행을 넣은 뒤 같은 규칙으로 토큰을 만든다. SSAFY OAuth 설정값은 비어 있으면 기동되지 않으므로 더미 값을 넣는다.
- 2018~2025 원본(ADR-0005)을 받아야 시작할 수 있다.
