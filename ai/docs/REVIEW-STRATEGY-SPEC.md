# 전략 도메인 명세 검토 — AI 서버 관점

대상: `docs/Strategy 도메인 명세서.md` (확정 명세)
검토일: 2026-09-02
검토 범위: **AI 서버가 DSL을 생성하고 검증하는 데 필요한 부분.** ERD, API 명세, 생명주기 정책은 다루지 않는다.

**전제.** 전략 도메인의 결정권은 전략팀에 있다. 명세와 우리 구현이 어긋나면 우리 쪽을 고친다. 이 문서는 어긋남과 공백을 찾아 목록으로 만든 것이지 반론이 아니다.

[REVIEW-STRATEGY-MVP.md](REVIEW-STRATEGY-MVP.md)는 명세 도착 전 MVP 초안을 본 것이라 이미 답이 온 항목이 섞여 있다. 이 문서가 최신이다.

| 표시 | 뜻 |
|---|---|
| **반영** | 명세대로 이미 구현했다. 확인만 하면 된다 |
| **질문** | 명세에 답이 없어 잠정값으로 짰다. 정해 주면 그대로 따른다 |
| **우리 몫** | 우리 쪽 사정. 전략팀이 볼 필요는 없지만 알고 있으면 좋다 |

---

## 요약 — 급한 것 셋

1. **Factor 계산 정의가 비어 있다.** Volatility 연율화, Drawdown 부호, 동점 처리 셋이다. 이 부류는 **화면에 오류로 안 뜨고 조용히 틀린 숫자로만 나타난다.** 정해지기 전에는 백테스트 결과를 신뢰할 수 없다
2. **필터 트리에 상한이 없다.** 재귀 구조라 깊이와 노드 수가 무제한이다. 우리가 잠정값을 걸었는데 백엔드와 값이 다르면 한쪽이 통과시킨 전략을 다른 쪽이 거부한다
3. **`period` 상한이 보유 데이터와 맞는지 모른다.** 명세는 `> 0`만 정한다. 데이터가 없는 기간을 요청하면 사용자는 "결과가 왜 비었지"만 본다

작성 전에 develop의 문서를 전부 훑었다. 「랭킹형 투자전략 시스템 설계안」, 「Strategy 도메인 및 Strategy DSL 설계」, 「백테스팅 서버 명세서」, 「코인 데이터 흐름」에서 답이 있는지 확인했고, **Volume Ratio 하나는 이미 답이 있어 질문에서 뺐다**(B-1 끝부분). 문서 간 불일치도 하나 발견해 B-4에 적었다.

# A. 반영한 것

명세대로 구현했다. `app/core/schema.py` 한 파일에 정의처를 두고, 검증기·프롬프트·계약 문서가 전부 거기서 값을 끌어간다.

| 항목 | 명세 | 구현 |
|---|---|---|
| `timeframe` | 6장 `1H` `4H` `1D` | 열거형 3값 |
| 필터 트리 | 7장 GROUP/CONDITION 재귀 | discriminated union + 전방 참조 |
| Operand | 9장 FACTOR/VALUE | discriminated union |
| Factor | 10장 6종 | 열거형 6값 |
| Operator | 11장 | 열거형 |
| `ranking` | 12장 factor·period·direction | 그대로 |
| `selection.topN` | 13장 `> 0` | `> 0`, 상한은 아래 질문 3 |
| `rebalance.period` | 14장 3값 | 열거형 3값 |
| Validation | 17장 | 필수·범위 전부 |

명세 5장의 예시 JSON이 그대로 검증을 통과한다. 알 수 없는 필드는 거부한다.

**우리 임시안에 있던 `universe`·`risk`·`portfolio`는 만들지 않았다.** 명세에서 빠졌으므로 따랐다.

**`period`가 봉 개수라는 점도 그대로 따랐다.** `timeframe`에 `1D`가 있어서 "20일 수익률"이 `timeframe: 1D, period: 20`으로 표현된다. 사용자가 말한 숫자를 LLM이 옮기기만 하면 되고, 봉 환산을 시킬 일이 없다. 환산을 시켰다면 위험했을 것이다 — 120을 넣어야 할 자리에 20이 들어가도 20은 유효한 정수라 검증에 안 걸리고 결과만 조용히 틀린다.

# B. 답이 필요한 것

## B-1. Factor 계산 정의 셋 — 제일 급하다

확정 명세 10장이 Factor 이름과 의미를 정하지만 계산 방식은 정하지 않는다. 다른 문서를 뒤져 보니 일부는 제안 단계로 남아 있고 하나는 이미 답이 있었다.

우리는 DSL을 만들 뿐 계산하지 않으므로 구현이 막히지는 않는다. 다만 **백테스트 결과의 의미가 여기서 갈린다.**

| # | 항목 | 현재 문서 상태 | 우리 선호 |
|---|---|---|---|
| 1 | Volatility 연율화 여부 | 「랭킹형 투자전략 시스템 설계안」 9.4가 "정확한 계산 정의를 하나로 고정해야 한다"며 **예시로** N기간 수익률 표준편차를 든다. 연율화 언급은 없다 | **연율화하지 않는다.** `timeframe` 단위 그대로 |
| 2 | Drawdown 부호 | 같은 문서 9.6이 "**DSL 설계 시 하나로 통일해야 한다**"고 미결을 명시한다. 다만 예시는 `DRAWDOWN(60) > -20%`로 음수를 쓴다 | **음수.** `-0.2` = 20% 하락 |
| 3 | 동점 처리 | 어느 문서에도 없다 | **거래대금 내림차순 → 심볼 사전순** |

**1번을 연율화하지 않는 이유** — 연율화하면 같은 임계값이 `1H`와 `1D`에서 다른 뜻이 된다. 사용자가 "변동성 0.05 이하"라고 할 때 어느 쪽인지 알 수 없다.

**2번은 어느 쪽으로 가도 되지만 정해야 한다.** 부호가 방향을 담으면 "20% 넘게 빠진 건 빼자"가 `DRAWDOWN GT -0.2`로 다른 Factor와 같은 방향으로 읽힌다. 이미 예시가 음수를 쓰고 있으니 그대로 굳히는 것이 자연스럽다.

**3번이 안 정해지면 백테스트가 재현되지 않는다.** 정렬이 불안정하면 같은 전략을 두 번 돌려 다른 수익률이 나온다.

### Volume Ratio는 답이 있었다 — 확인만 부탁한다

「랭킹형 투자전략 시스템 설계안」 9.5가 공식(`현재 거래량 / 최근 N기간 평균 거래량`)을 주지만 "현재 거래량"이 어느 봉인지는 적지 않는다.

그런데 「백테스팅 서버 명세서」 7장 Look-Ahead 방지가 이렇게 못 박는다.

```
Candle t 종료 → Factor 계산 → Filter/Ranking → 주문 결정 → Candle t+1에서 가상 체결
```

이 원칙대로면 **직전 완결 봉**이 답이다. 진행 중인 봉을 쓰면 룩어헤드가 된다. 우리는 그렇게 이해하고 있다. 다른 뜻이면 알려 달라.

## B-2. 필터 트리와 선택 개수 상한

명세 17장은 `GROUP.children` 최소 1만 정하고 상한이 없다. 재귀 구조라 깊이도 무제한이다. `selection.topN`도 `> 0`만 있다.

**상한이 없으면 안 된다.** LLM이 5단 중첩 트리를 만들면 검증은 통과하는데 사용자는 화면에서 이해하지 못하고 토큰만 는다.

우리가 걸어 둔 잠정값이다.

| 항목 | 잠정값 | 근거 |
|---|---|---|
| 트리 깊이 | 2 | 명세 5장 예시가 정확히 깊이 2다 |
| CONDITION 총 개수 | 5 | 화면에서 사람이 읽을 수 있는 한계 |
| `GROUP.children` | 1~5 | — |
| `selection.topN` | 30 | 유니버스 규모(거래대금 상위 20~30종목)와 맞춘 값 |

**값 자체보다 백엔드와 같은 값을 쓰는 것이 중요하다.** 우리가 깊이 3을 통과시켰는데 백엔드가 거부하면, 사용자는 이미 LLM 호출 비용을 치른 뒤 실패만 본다. 반대로 우리가 더 좁으면 백엔드가 받을 전략을 우리가 막는다.

우리가 먼저 거는 이유는 재시도 루프 안에서 잡아야 LLM이 그 자리에서 평평하게 고쳐 오기 때문이다. 백엔드만 걸면 사용자에게는 그냥 실패다.

**늘리는 건 쉽고 줄이는 건 어렵다.** Strategy가 Immutable Snapshot이라 이미 저장된 전략이 나중 상한에 걸리면 다시 돌릴 수 없다. 좁게 시작해서 필요하면 푸는 방향을 제안한다.

## B-3. `period` 상한 — 데이터 파트에 묻는다

명세 17장은 `period > 0`만 정한다.

상한이 없으면 LLM이 `period: 2000`을 넣을 수 있다. 그만한 과거 데이터가 없으면 Factor가 계산되지 않거나 종목 대부분이 후보에서 빠지고, 사용자는 결과가 빈 이유를 모른다.

우리 잠정값이다. **보유 데이터 기간을 모르고 정한 숫자라 확인이 필요하다.**

| timeframe | 잠정 상한 | 환산 |
|---|---|---|
| `1H` | 720 | 30일 |
| `4H` | 540 | 90일 |
| `1D` | 365 | 1년 |

**질문은 하나다. 수집이 몇 개월치인가.**

워밍업은 이미 처리돼 있는 것으로 확인했다. 「백테스팅 서버 명세서」 7장이 "Factor 계산에 과거 데이터가 추가로 필요한 경우 Warm-up 데이터를 조회한다. Warm-up 데이터는 지표 계산에만 사용하며 해당 기간에는 거래를 수행하지 않는다"로 정의한다. 그러면 상한은 워밍업까지 포함해 조회 가능한 구간 안에 들어가야 한다.

## B-4. 문서 간 불일치 하나 — 리밸런싱 주기

「백테스팅 서버 명세서」의 **추후 확정 항목**에 `지원 Rebalancing 주기`가 남아 있다.

그런데 확정 명세 14장은 `DAILY` / `WEEKLY` / `MONTHLY` 세 값으로 이미 정했고, 우리는 그대로 열거형에 넣었다.

어느 쪽이 최신인지 확인해 달라. 백테스트 쪽에서 값이 늘거나 줄면 우리 열거형도 따라가야 한다.

같은 목록의 `Universe 거래대금 산정 기간`, `최종 체결가격 기준`, `Slippage 모델`은 DSL에 해당 필드가 없어 우리와 무관하다.

# C. 우리 몫

전략팀이 결정할 일은 아니지만 알고 있으면 좋은 것들이다.

## C-1. 구조화 출력을 쓸 수 없다

LLM에게 JSON 형식을 강제하는 기능(`response_format`의 `strict` 모드)을 쓰려 했는데 **GMS 게이트웨이가 거부한다.**

```
'oneOf' is not permitted. (context: properties.left)
```

`CONDITION.left`·`right`가 FACTOR 또는 VALUE 둘 중 하나라 스키마에 `oneOf`가 생기는데, strict 모드가 그것을 허용하지 않는다. 명세 구조 자체가 원인이지만 **명세를 바꿔 달라는 뜻은 아니다.** 표현력이 필요한 구조이고, 우리 쪽에서 감당할 수 있다.

결과적으로 형식 보증이 사라져서, 모델이 코드 펜스나 설명 문장을 섞어 보내도 우리가 정제해서 받아낸다. 형식 오류가 재시도 사유에 포함되므로 응답 시간과 크레딧 소모가 조금 는다.

## C-2. 사용자가 실제로 말하는 길이

전략 요청 자연어를 34건 모아 재보니 **평균 22.5자, 최대 37자**였다.

```
거래량 상위 코인 중 최근 모멘텀이 가장 강한 5개에 투자하고 싶어   (37자)
손실은 짧게 끊고 상승 추세는 오래 가져가는 전략을 만들어줘        (33자)
```

화면 입력창 설계에 참고가 될 수 있다. 목록은 `ai/tests/fixtures/user_inputs.md`에 있고, 갈래와 출처를 붙여 뒀다.

**"전략이 아닌 입력"과 "지원 범위 밖 요청"이 34건 중 8건이다.** "안녕", "비트코인 지금 사도 됨?", "5% 빠지면 사고 10% 오르면 팔아" 같은 것들이다. 마지막 유형은 진입·청산 신호형이라 우리 DSL로 표현되지 않는다.

우리는 이런 입력도 거부하지 않고 전략을 만든다. 대신 임의로 정한 값을 응답의 `assumptions`에 한 줄씩 담는다. 사용자가 말하지 않은 값이 채워졌다는 사실을 알리는 통로다. **화면에 이 필드를 보여줄 자리가 필요하다.**

## C-3. 응답에 담는 것

DSL 외에 우리가 함께 보내는 값들이다.

| 필드 | 내용 |
|---|---|
| `changes` | 수정 요청일 때 무엇이 바뀌었는지. 두 전략 객체를 비교해 서버가 만든다 |
| `assumptions` | 서버가 임의로 정한 값 |
| `attempts` | 시도 횟수 |
| `elapsedMs` | 소요 시간 |

`changes`를 LLM에게 만들게 하지 않는 이유는 **LLM이 바꿨다고 말한 것과 실제로 바뀐 것이 다를 수 있어서다.**

# D. 답이 필요한 시점

지금 개발은 막히지 않는다. 잠정값이 전부 한 곳(`app/core/schema.py` 상단 상수)에 모여 있어 답이 오면 숫자만 바꾸면 된다.

**막히는 지점은 골든 케이스와 프롬프트 튜닝이다.** 자연어 입력에 기대 DSL을 붙여 정답지를 만들고 통과율을 재는 단계인데, 기대 DSL을 적으려면 위 값들이 확정돼야 한다.

우선순위는 B-1 → B-3 → B-2 순이다. B-1이 결과의 의미를 바꾸고, B-3은 결과가 비는 원인이 되며, B-2는 범위 조정이라 뒤로 밀 수 있다.
