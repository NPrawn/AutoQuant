## 이 구간의 성격

Epic H가 develop에 들어갔다(`dbcaf71`). 서버가 실제로 응답한다.

**그런데 얼마나 맞히는지 말할 근거가 없다.** 프롬프트 4개가 합쳐서 31줄이고 구조 지시뿐이다. 스키마가 필드와 허용값을 주지만 "5%"를 `5`로 쓸지 `0.05`로 쓸지는 아무도 안 알려준다.

이 구간이 끝나면 **정확도를 숫자로 말할 수 있다.** L-2 튜닝은 그 숫자를 올리는 일이고, 지금은 잴 도구가 없어서 시작할 수 없다.

## 정의처는 백엔드 엔진 구현이다

전략팀에 물어보려던 계산 정의가 이미 코드에 있다. 주석까지 달려 있다.

`backend/api/src/main/java/com/ssafy/a107/strategy/engine/factor/Ta4jFactorCalculator.java`

| Factor | 공식 | 단위 |
|---|---|---|
| `RETURN` | `((현재 종가 / N기간 전 종가) - 1) * 100` | 퍼센트 |
| `RSI` | ta4j RSIIndicator (Welles Wilder) | 0~100 |
| `SMA_DISPARITY` | `((현재 종가 / SMA(종가, N)) - 1) * 100` | 퍼센트 |
| `VOLATILITY` | 최근 N개 1캔들 수익률(%)의 모집단 표준편차 | 퍼센트 |
| `VOLUME_RATIO` | `현재 캔들 거래량 / SMA(거래량, N)` | **배수** |
| `DRAWDOWN` | `((현재 종가 / 최고 종가) - 1) * 100` | 퍼센트, 음수 |

동점 처리는 `RankingEvaluator`의 `RankingComparator`에 있다. 값이 같으면 `assetId` 오름차순이다.

**추측해서 적지 마라.** 위 표와 다른 값이 필요하면 그 파일을 다시 읽는다.

## 값 스케일이 이 구간의 최대 위험이다

```
"20% 넘게 빠진 건 빼줘"
  DRAWDOWN(60) GT -20      맞다
  DRAWDOWN(60) GT -0.2     0.2% 하락으로 읽힌다. 100배 틀린다

"거래량 1.5배 이상"
  VOLUME_RATIO(20) GT 1.5  맞다
  VOLUME_RATIO(20) GT 150  150배로 읽힌다
```

**둘 다 유효한 실수라 검증을 통과한다.** `-115`에서 상한까지 걷어내 범위 검사도 없다. 화면에 오류로 안 뜨고 백테스트 숫자만 조용히 틀린다.

지금 이걸 잡는 장치가 하나도 없다. **프롬프트가 막고 골든 케이스가 잰다.** 그래서 `-117`이 먼저다.

프롬프트가 스케일을 정해야 정답지의 기대값이 그 기준으로 적힌다. 정답지가 있어야 러너가 잴 대상이 생긴다.

# K-3 프롬프트 도메인 규칙 (5h, `-117`)

## 티켓에 있는 것

Factor 여섯의 스케일 표, `period`가 캔들 개수라는 것, 지표별 관행값, 기본값 정책, 지원 범위 밖 요청 처리. 완료 조건 여섯 개.

## 환산 규칙을 쓰지 마라

`timeframe`이 `1D`·`4H`·`1H` 셋이므로 **사용자가 말한 단위에 맞는 `timeframe`을 고르면 환산이 필요 없다.**

| 사용자 말 | timeframe | period |
|---|---|---|
| 20일 수익률 | `1D` | 20 |
| 4시간봉 RSI 14 | `4H` | 14 |
| 최근 일주일 | `1D` | 7 |

"4H면 곱하기 6" 같은 지시를 넣으면 **LLM에게 산수를 시키게 되고, 틀려도 검증에 안 걸린다.** 스케일 오류와 같은 종류의 조용한 실패가 하나 더 생긴다.

## 장황하게 쓰지 마라

규칙이 길수록 토큰이 늘고 모델이 더 잘 지키지도 않는다. **스케일 표와 기본값 표가 본체이고 나머지는 한 줄씩이면 된다.**

현재 시스템 프롬프트가 1,270토큰이다. 이 숫자가 두 배가 되면 골든 케이스 한 회차 비용도 두 배가 된다(아래 L-1 참조). 작성 후 실제 GMS 호출로 `usage.prompt_tokens`을 다시 재서 완료 보고에 적는다.

## 파일을 새로 둘지는 재량이다

`system.txt`에 직접 넣어도 되고 도메인 규칙 파일을 따로 만들어 로더가 읽게 해도 된다. **새 파일을 만들면 `tests/test_prompt_templates.py`가 템플릿 4종을 정확히 요구하므로 그 테스트도 같이 고친다.** 자리표시자 규약(5개)은 그대로 지킨다.

## 완료 조건

티켓 `-117`의 여섯 개. 특히 "환산 규칙이 없다"와 "갱신 후 토큰 수가 완료 보고에 있다"를 빠뜨리지 않는다.

# K-4 골든 케이스 정답지 (8h, `-118`)

## 갈래별 집계 (실측)

`tests/fixtures/user_inputs.md` 34건을 세어 보면 이렇다.

| 갈래 | 건수 | 채점 |
|---|---|---|
| 조건이 붙은 요청 | 12 | 정확한 DSL |
| 여러 조건을 쌓는 요청 | 6 | 정확한 DSL |
| 단순 랭킹 요청 | 5 | 정확한 DSL |
| 모호한 요청 | 3 | 기본값이 채워지고 `assumptions`가 비어 있지 않은지 |
| 전략이 아닌 입력 | 4 | 아래 참조 |
| 지원 범위 밖 요청 | 4 | 통과율에서 분리 — 아래 참조, 실제로는 3건 |

정확한 DSL을 적는 것은 23건이다. **다만 아래 `U-33` 건을 반영하면 24건이 된다.**

## 비교 방식이 이 작업의 실질이다

기대 DSL과 실제 출력을 어떻게 비교할지가 통과율 숫자의 의미를 정한다.

완전 일치를 요구하면 `assumptions`로 채워진 기본값 때문에 거의 다 실패한다. 사용자가 말한 필드만 비교하는 편이 맞아 보이지만, **그러면 "말하지 않은 필드에 이상한 값이 들어간 것"을 못 잡는다.**

어느 쪽으로 갈지 정하고 근거를 완료 보고에 적는다. 절충안(핵심 필드는 정확 비교, 기본값 필드는 존재만 확인)도 가능하다.

## 짧은 경로가 정답지에 영향을 준다

**티켓 `-118`이 쓰인 뒤에 계약이 바뀌었다.** `-127`의 짧은 경로가 이제 전략을 만들지 않고 `strategy: null`을 반환한다([DECISIONS.md](DECISIONS.md) 결정 5 보충).

34건 중 **`U-28` "안녕하세요" 한 건이 짧은 경로 정확 일치 목록에 걸린다.** 이 건의 기대값은 "기본값이 채워지고 `assumptions`가 비어 있지 않다"가 아니라 **"`strategy`가 `null`이고 `assumptions`가 비어 있지 않고 `attempts`가 0"** 이다.

나머지 "전략이 아닌 입력" 3건("내 지갑 잔고가 얼마야", "오늘 코인 뉴스 알려줘", "비트코인 지금 사도 되나요")은 길이·목록 어느 쪽에도 안 걸려 LLM으로 간다. 기대값은 티켓대로다.

**정답지에 짧은 경로 여부를 표시하는 칸을 두는 편이 낫다.** 그래야 러너가 "이 건은 LLM을 안 부르는 게 정상"임을 알고, 통과율과 크레딧 계산이 어긋나지 않는다.

## `U-33`은 이제 지원 범위 밖이 아니다

`user_inputs.md`의 갈래 표시는 상한이 살아 있던 때 붙었다. **`U-33` "1000일 수익률이 높은 순으로 골라줘"가 지원 범위 밖으로 분류돼 있는데, `-115`에서 `MAX_PERIOD_1D = 365`를 걷어내 지금은 표현된다.** 일봉 데이터가 2018년부터 약 2,900개라 1000일도 계산된다.

이 건은 **단순 랭킹 요청으로 옮기고 정확한 DSL을 적는 편이 맞다.** 그러면 정확 채점이 24건, 지원 범위 밖이 3건이 된다.

`user_inputs.md`의 갈래 칸도 같이 고친다. 고치는 김에 나머지 3건도 지금 스키마로 정말 표현이 안 되는지 다시 본다 — `U-31`(진입·청산 신호형)과 `U-32`(수익률과 변동성 두 축 동시 최적화)는 여전히 범위 밖이 맞다. 랭킹이 팩터 하나뿐이라 두 축을 동시에 세울 수 없다.

## 지원 범위 밖 3건

통과율에서 뺀다. 정답 DSL이 존재하지 않아 넣으면 90% 목표가 구조적으로 불가능하고, 그냥 지우면 실제 입력의 12%를 측정에서 없애는 셈이다.

**별도 지표로 센다** — 거부하지 않고 전략을 만들었는가, `assumptions`에 지원 범위 밖이라는 사실이 담겼는가. 여기서 볼 것은 정확도가 아니라 동작이다.

# L-1 live 러너와 측정 (5h, `-119`)

## 기본 스위트에서 분리한다

`pyproject.toml`의 `[tool.pytest.ini_options]`에 지금 `testpaths`만 있다. `markers`에 `live`를 등록하고 `addopts`로 기본 제외를 건다.

```bash
python -m pytest              # live 제외
python -m pytest -m live      # live만
```

이유가 둘이다. GMS 키 없는 환경에서 기본 스위트가 깨지면 안 되고, 매번 크레딧을 태우면 안 된다.

## 총량 차단이 러너를 막는다 — 티켓에 없는 함정

`-127`이 넣은 **분당 30회 제한이 골든 케이스 러너에 그대로 걸린다.** 33건(짧은 경로 1건 제외)을 연속으로 돌리면 30건째부터 429다. 재시도가 붙으면 더 빨리 닿는다.

429는 `LLMCreditLimitError`고 서버가 자기 방어로 낸 것이라 **골든 케이스 실패로 세면 안 된다.** 그걸 실패로 세면 통과율이 우리 방어선 때문에 떨어진다.

셋 중 하나를 고르고 근거를 완료 보고에 적는다.

- 러너가 호출 간격을 둔다 — 가장 단순하고 서버를 손대지 않는다. 회차 실행이 2분쯤 걸린다
- 러너가 429를 만나면 기다렸다가 재시도한다 — 실패로 안 세되 시간이 늘어난다
- 테스트에서 상한 상수를 올린다 — 실행은 빠르지만 실제 운영 경로와 다른 조건에서 재게 된다

**어느 쪽이든 429가 통과율에 섞이지 않는 것이 조건이다.**

## 한 회차 비용을 알고 시작한다

시스템 프롬프트가 1,270토큰이고 골든 케이스가 33건이다. 재시도가 없어도 **한 회차에 약 42,000 프롬프트 토큰**이다. `-117`에서 프롬프트가 길어지면 이 숫자가 같이 는다.

L-2 튜닝은 이걸 회차마다 반복한다. **크레딧이 팀 공유라 회차 수를 세면서 돌려야 한다.**

## 무엇을 재는지

티켓 `-119`의 표를 따른다. 통과 건수, 갈래별, 출처별, 실패 원인 분류, 평균 시도 횟수, 응답 시간 중앙값과 상위 95%.

**출처별을 빠뜨리지 마라.** `user_inputs.md`에 팀원 27건, 작성 7건이 표시돼 있다. 팀원 원문에서만 통과율이 떨어지면 프롬프트가 우리가 다듬은 문장에만 맞춰진 것이다. 그건 실제 사용자 앞에서 무너진다.

**실패 원인을 형식·값·스케일로 나눈다.** 스케일 오류가 몇 건인지가 `-117`이 제 역할을 했는지 판정한다.

**응답 시간은 L-4에서 Spring 타임아웃을 정하는 근거다.** 지금 `LLM_TIMEOUT_SECONDS = 30`은 근거 없는 값이다.

## 1회차 숫자가 나쁜 것은 실패가 아니다

이 작업은 재는 도구까지다. **숫자가 나쁘게 나와도 그것이 기준선이다.** 기준선을 만들지 않고 튜닝부터 하면 좋아졌는지 말할 수 없다.

결과를 회차 구분이 되는 형태로 파일에 남긴다. 위치와 형식은 재량이다.

# 반려 사유 정리

1. Factor 스케일을 `Ta4jFactorCalculator` 확인 없이 추측해서 적음
2. 프롬프트에 timeframe 환산 규칙을 넣음
3. DSL 필드명·허용값을 `app/core/schema.py` 밖에서 문자열로 다시 적음 — 프롬프트는 자리표시자로 스키마를 주입받는다
4. 골든 케이스 기대 DSL이 스키마 검증을 통과하지 못함
5. 지원 범위 밖 4건을 통과율에 섞음
6. 429를 골든 케이스 실패로 셈
7. live 테스트가 기본 스위트에서 돌아 GMS 키 없는 환경이 깨짐
8. 측정 기록 없이 좋아졌다고 보고함
9. 완료 보고에 커밋 SHA가 없음
