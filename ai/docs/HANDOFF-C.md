# S-1 스키마 잠정 상한 정리 (3h)

## 만들 것

`app/core/schema.py`의 잠정 상한 여섯 개를 걷어내고 하나만 남긴다. `tests/test_schema.py`에서 대응 케이스를 정리한다.

```
제거: MAX_CONDITIONS  MAX_GROUP_CHILDREN  MAX_TOP_N
      MAX_PERIOD_1H   MAX_PERIOD_4H       MAX_PERIOD_1D

남김: MAX_FILTER_DEPTH = 5   # 파서 방어선. 도메인 규칙이 아니다 (2 → 5)
```

## 왜 걷어내나

이 숫자들은 [-90](https://ssafy.atlassian.net/browse/S15P21A107-90)에서 모르는 값을 보수적으로 잡은 것이다. 그 뒤 사실 셋이 드러났다.

**백엔드에도 상한이 없다.** `backend/api`의 `GroupFilterNode`는 `@NotEmpty`뿐이고 `FactorOperand`는 `period > 0`만 본다. [Strategy 도메인 명세서](../../docs/Strategy%20도메인%20명세서.md) 17장과 같다. **우리만 좁았다.**

**데이터는 2018년부터 8년치가 있다.** `period` 상한을 데이터 부족으로 정당화할 수 없다.

| timeframe | 8년치 봉 수 | 우리가 건 상한 |
|---|---|---|
| `1H` | 약 70,000 | 720 |
| `4H` | 약 17,000 | 540 |
| `1D` | 약 2,900 | 365 |

**`topN` 상한은 의미가 없다.** 명세 13장이 "`topN`은 최대 선택 종목 수이며 N개를 강제로 채우지 않는다"고 정한다. 후보가 5개인데 `topN: 100`이면 5개를 산다.

`period` 상한은 애초에 우리 결정 사항이 아니다. 그 값으로 백테스트를 돌리는 건 백엔드고, 상한을 정하는 요인(데이터 조회 범위, 워밍업, 계산 비용)이 전부 실행하는 쪽에 있다.

**우리가 명세보다 좁으면 백엔드가 받을 전략을 우리가 거부한다.** 그 거부는 조용하지 않다 — 검증 실패로 잡혀 재시도를 태우고 사용자는 이유를 모르는 오류를 받는다.

## 깊이만 남기는 이유

성격이 다르다. 나머지는 숫자 하나라 값이 크든 작든 파서가 감당한다. **트리 깊이는 재귀 파싱이라 병리적으로 깊은 입력이 오면 스택을 태운다.**

즉 이 값은 백엔드와 합의할 도메인 규칙이 아니라 우리 파서를 지키는 선이다. 2에서 5로 넓힌다. `tests/fixtures/user_inputs.md` 34건(평균 22자)에 깊이 3 이상을 요구하는 문장이 없어 넘을 일이 없다.

**상수 옆에 그 취지를 주석으로 남겨라.** 나중에 "왜 이것만 있나"는 질문이 반드시 나온다.

## 검증 규칙을 명세 범위로

| 필드 | 바꿀 검증 |
|---|---|
| `FactorOperand.period` | `> 0`만 |
| `Ranking.period` | `> 0`만 |
| `Selection.topN` | `> 0`만 |
| `FilterGroup.children` | 최소 1만 |

`Strategy.validate_limits`에서 `max_periods` 딕셔너리, `periods` 수집, `conditions` 카운트가 모두 빠진다. 트리를 도는 목적이 깊이 검사 하나로 줄어든다.

## `MAX_USER_INPUT_LENGTH`는 건드리지 않는다

500자는 잠정값이 아니라 우리 방어선이다. 토큰 폭주를 막고 실측(발화 34건, 최대 37자)에 근거가 있다.

문서 쪽이 2000자로 어긋나 있던 것은 이 인계 명세와 같은 MR에서 500으로 맞췄다. `PLAN.md`, `TASKS.md`, `DECISIONS.md`.

## 테스트 정리

제거한 상한의 경계값·거부 케이스를 지운다. 깊이 케이스는 3 거부에서 **6 거부, 5 통과**로 바꾼다.

`period`와 `topN`의 하한 케이스(0, 음수 거부)는 남긴다. 명세가 `> 0`을 정하므로 계속 유효하다.

## 완료 조건

- 상수가 `MAX_FILTER_DEPTH` 하나만 남고 취지가 주석으로 적혀 있다
- `period`, `topN`이 `> 0`만 검증한다
- 깊이 6 트리가 거부되고 깊이 5는 통과한다
- 제거한 상한의 테스트 케이스가 정리된다
- `python -m pytest`가 GMS 키 없는 환경에서 통과한다

# H-1 의존성 주입 (3h, `-125`)

## 만들 것

`app/api/deps.py`. 설정과 `translate()`를 라우터에 주입하고, 테스트에서 갈아 끼울 수 있게 한다.

## 라우터가 직접 임포트하지 마라

`app/api/v1/strategy.py`가 `from app.services.translator import translate`를 직접 하면 테스트가 실제 LLM을 부르게 된다. FastAPI `Depends`로 받아 `app.dependency_overrides`로 바꿔 끼운다.

`app/services/llm_client.py`를 monkeypatch하는 방식으로 때우지 마라. 그건 서비스 내부 사정이라 구현이 바뀌면 테스트가 같이 깨진다.

## `deps.py`에 로직을 넣지 마라

무엇을 주입할지만 정한다. 재시도 정책과 검증은 이미 각자 자리에 있다.

## `detail.attempts`를 싣는다 (2026-09-03 확정)

`-125`·`-128`의 완료 조건에는 없지만 [TASKS.md](TASKS.md) H-3 케이스 5가 요구하고, **지금 구조로는 낼 수 없다.** `translate()`가 소진되면 `DSLValidationError(format_user_errors(...))`로 문자열 하나만 던지고 시도 횟수를 버린다.

`DSLValidationError`가 시도 횟수와 마지막 오류 목록을 갖도록 넓히고 `app/api/error_handlers.py`가 `detail`에 싣는다. 키는 `attempts`·`lastErrors`로 camelCase 통일 ([DECISIONS.md](DECISIONS.md) 결정 6).

**이 작업은 H-1 커밋에 얹는다.** 예외 구조를 바꾸는 일이라 엔드포인트보다 먼저다.

Pydantic `errors()` 원문을 그대로 실으면 내부 구조가 API로 새어 나간다. `format_user_errors()`를 거친 문자열만 싣는다.

## 완료 조건

- `app/api/deps.py`가 translator를 반환하는 의존성을 제공한다
- 테스트가 `dependency_overrides`로 가짜 translator를 끼울 수 있다
- 이 파일에 비즈니스 로직이 없다

# H-2 변환 엔드포인트 (5h, `-126`)

## 만들 것

`app/api/v1/strategy.py`에 `POST /api/v1/ai/strategies/translate`. `app/main.py`에 라우터 등록.

## 라우터는 얇다

라우터가 하는 일은 셋이다. 요청 모델을 받고, 주입받은 translator를 부르고, `TranslateResponse`로 감싼다.

**분기를 라우터에 두지 마라.** 신규 생성과 수정을 가르는 것은 `currentStrategy`의 유무인데, 그 판단은 이미 `translate()` 안에 있다. 라우터에서 한 번 더 보면 정책이 두 군데로 흩어진다.

**재시도 소진 판정도 라우터에 두지 마라.** `translate()`가 `DSLValidationError`를 던지고 C-2 핸들러가 422로 바꾼다. 경로가 이미 이어져 있다.

`app/main.py`는 라우터 등록까지다. 비즈니스 로직이 들어가면 반려한다.

## 상태 코드는 이미 정해져 있다

| 상황 | 상태 | 코드 |
|---|---|---|
| 성공 | 200 | — |
| 요청 본문 검증 실패 | 400 | `INVALID_REQUEST` |
| 재시도 소진 | 422 | `DSL_VALIDATION_FAILED` |
| LLM 타임아웃 | 504 | `LLM_TIMEOUT` |
| LLM 업스트림 오류 | 502 | `LLM_UPSTREAM_ERROR` |
| 총량 초과 | 429 | S-2에서 새로 정한다 |

앞의 다섯은 C-2·C-3 핸들러가 이미 처리한다. **엔드포인트에서 예외를 잡아 응답으로 바꾸지 마라.** 그러면 변환이 두 군데가 된다.

## 신규 생성 시 `changes`는 빈 목록이다 (2026-09-03 확정)

`describe_changes(None, ...)`가 지금처럼 `[]`를 돌려주는 것이 맞다. **코드와 테스트를 바꾸지 마라.** [TASKS.md](TASKS.md) G-6 케이스 1의 "신규 생성 표시" 요구는 내렸다.

프론트는 `currentStrategy`를 보냈는지 이미 안다. 서버가 "신규 생성했습니다"를 넣으면 프론트가 이미 가진 정보를 문자열로 돌려주는 것이고, 그 문자열을 프론트가 다시 파싱하게 된다.

## CORS를 넣지 마라

프론트는 Spring만 호출하고 Spring이 이 서버를 부른다. 브라우저가 직접 올 일이 없으니 CORS 미들웨어를 넣는 건 **열지 않아도 될 문을 여는 것**이다.

## `meta`를 다시 만들지 마라

`translate()`가 반환하는 결과에서 `value`와 `meta`를 꺼내 `TranslateResponse`로 감싼다. `meta`는 translator가 이미 채웠다.

## 완료 조건

- `POST /api/v1/ai/strategies/translate`가 200으로 `strategy`와 `meta`를 반환한다
- `currentStrategy`를 보내면 수정 경로로 간다
- 엔드포인트에 `try/except`가 없다
- `app/main.py`에 비즈니스 로직이 없다
- CORS 미들웨어를 넣지 않는다
- translator를 주입받는다. 직접 임포트하지 않는다

# S-2 GMS 크레딧 방어 — 짧은 경로와 총량 차단 (4h, `-127`)

## 지키려는 것

**GMS 크레딧이다. 팀 공유고 유한하다.** 호출당 약 1,270 프롬프트 토큰이라 장난 100회면 127,000토큰이 날아간다. 시연 중에 소진되면 그날 데모가 끝난다.

## 무엇을 넣고 무엇을 안 넣나

| 방어 | 어디 |
|---|---|
| 사용자당 호출 제한 | **Spring.** 우리는 무상태라 사용자별 카운터를 들 수 없다 |
| 입력 길이 상한 500자 | 이미 있다 (`TranslateRequest`) |
| 인사말 짧은 경로 | **여기** |
| 프로세스 총량 차단 | **여기** |

뒤의 둘은 사용자별이 아니라 서버 전체를 본다. 사용자 상태가 아니라 프로세스 자기 보호라 무상태 원칙과 부딪치지 않는다.

## 1. 인사말 짧은 경로

LLM을 아예 부르지 않고 즉시 응답한다. 아끼는 것이 입력 21토큰이 아니라 **호출 한 건 전부(약 1,270토큰)** 다.

**결정 5를 깨지 않는다.** 거부하는 게 아니라 코드가 기본 전략과 `assumptions`를 만들어 반환한다. 결정 5는 "거부하지 않고 전략을 만든다"이지 "LLM을 반드시 부른다"가 아니다.

**판정을 아주 좁게 잡는다.** 인사말 정확 일치 목록("안녕", "안녕하세요", "hi", "hello", "테스트", "test")과 공백 제외 3자 이하까지다. 부분 일치나 포함 관계로 판정하지 마라.

넓게 잡으면 손해가 커지는 구조다. **"돈 많이 버는 전략"은 모호하지만 진짜 요청이고, 여기 걸리면 그게 최악의 오답이다.** 사용자는 자기 요청이 무시된 줄도 모른다. `tests/fixtures/user_inputs.md`의 "전략이 아닌 입력" 4건 중에서도 명백한 것만 목록에 넣는다 — "비트코인 지금 사도 됨?"은 전략 요청이 아니지만 투자 의도가 있으니 LLM에게 보낸다.

`meta.attempts`는 0으로 둔다. **LLM을 부르지 않았다는 사실이 드러나야 L-2 측정이 오염되지 않는다.**

## 2. 프로세스 총량 차단

서버 전체의 분당 호출 수가 상한을 넘으면 429다. 사용자를 구분하지 않는다.

카운터 하나와 시간 창 하나면 된다. **외부 저장소를 쓰지 않는다** — 무상태 원칙이고 Redis에 붙지 않는다는 규칙이 있다. 라이브러리도 추가하지 않는다.

**분당 30회로 확정했다** ([DECISIONS.md](DECISIONS.md) 결정 6). 모듈 상단 상수 한 곳에 둔다. 정상 사용이 닿지 않으면서 폭주는 막는 선이다.

**이것은 방어선이지 정책이 아니다.** 정상 사용자가 여기 걸리면 상한이 잘못 잡힌 것이다.

## 429 코드를 새로 정한다

`app/core/errors.py`의 예외는 지금 4종이고 429가 없다. 하나 늘리고 C-2 핸들러에 등록한다. 기존 4종과 같은 형태 — 상태 코드와 코드 문자열을 속성으로 갖는다.

`code` 문자열은 Spring이 분기하는 값이라 정하면 안 바꾼다. **엔드포인트에서 직접 429를 만들지 마라.**

## 요청이 비용을 정하게 만들지 마라

`TranslateRequest`에 재시도 횟수·모델·타임아웃 필드를 넣지 않는다. 지금 없고 앞으로도 없어야 한다. 있으면 호출자가 우리 크레딧 소모량을 정한다. `settings.max_retries`와 `settings.llm_timeout_seconds`가 유일한 통제점이다.

## 완료 조건

- 인사말 목록에 정확히 일치하는 입력이 LLM 호출 없이 응답된다 — **테스트가 호출 횟수를 센다**
- 그때 `meta.attempts`가 0이고 `assumptions`가 채워진다
- "돈 많이 버는 전략" 같은 모호한 요청은 짧은 경로에 걸리지 않는다
- 분당 총 호출이 상한을 넘으면 429가 나가고 `code`·`message`·`detail` 형태를 지킨다
- 429 코드가 `errors.py`에 정의되고 핸들러에 등록된다
- 상한값이 모듈 상단 상수 한 곳에 있다
- 외부 저장소를 쓰지 않는다
- 총량 차단이 헬스 엔드포인트를 막지 않는다

# H-3 API 테스트 (5h, `-128`)

## 덮어야 할 케이스

`-128`에 13건이 적혀 있다. 그대로 따른다. 성공 경로 4건(`meta` 여섯 필드가 다 있는지, 필드명이 camelCase인지 포함), 오류 6건, 새는 것 4건, 남용 방어 3건, 요청 ID 2건이다.

**이 테스트가 백엔드와의 계약을 지키는 유일한 장치다.** L-3에서 OpenAPI를 뽑기 전까지 여기가 계약서다.

두 가지를 특히 놓치기 쉽다.

**요청 ID를 이어받는지.** `X-Request-ID`를 보내면 그 값이 돌아와야 하고, 안 보내면 생성돼 돌아와야 한다. **우리가 덮으면 Spring 쪽 추적이 끊긴다.** C-4에서 구현했지만 이 엔드포인트에서도 도는지 다시 본다.

**짧은 경로에서 translator가 안 불린 것.** 200이 나왔다는 것만으로는 짧은 경로를 탔는지 알 수 없다. 호출 횟수를 세라.

## 실제 API를 치지 마라

`tests/`는 GMS 키가 없는 환경에서 통과해야 한다. 실전 호출은 L-1의 `test_live.py`로 따로 뺀다.

`tests/fixtures/llm_responses.py`에 이미 응답 표본이 있다. 새로 만들지 말고 가져다 쓴다.

## 상태 코드만 보지 마라

`assert response.status_code == 422` 하나로 끝내면 3번과 4번이 같은 테스트가 된다. **`code` 문자열까지 본다.** 그게 Spring이 분기하는 값이라 계약의 실체다.

## 완료 조건

- `-128`의 13개 케이스가 모두 있다
- 오류 케이스에서 상태 코드와 `code` 문자열을 함께 확인한다
- 오류 응답 본문에 스택 트레이스·API 키·Pydantic 원문이 없다
- `python -m pytest`가 GMS 키 없는 환경에서 통과한다. 실제 API를 치지 않는다

# 반려 사유 정리

1. `app/core/config.py` 밖에서 `os.environ`을 읽음
2. DSL 필드명·허용값을 `app/core/schema.py` 밖에서 문자열로 다시 적음
3. 라우터가 `translate`를 직접 임포트해 테스트에서 갈아 끼울 수 없음
4. 라우터나 `main.py`에 비즈니스 로직이 들어감
5. 테스트가 실제 LLM API를 호출함
6. 엔드포인트가 예외를 잡아 응답으로 바꿈 — 변환은 핸들러 한 곳이다
7. 총량 차단 값이나 남긴 상한의 근거를 `DECISIONS.md`에 안 적음
8. 완료 보고에 커밋 SHA가 없음

# 열려 있는 질문

착수를 막던 셋(`detail.attempts`, 신규 생성 `changes`, 총량 차단 값)은 2026-09-03에 확정했다. [DECISIONS.md](DECISIONS.md) 결정 6과 각 절을 본다.

**서킷 브레이커가 닫힌 티켓과 함께 사라졌다.** `-120`의 하위 작업 `-122`는 "짧은 경로, 총량 차단, **서킷 브레이커**"였는데 `-127`에는 앞의 둘만 남았다. 제외 범위에도 안 적혀 있어 의도적으로 뺀 것인지 불분명하다.

목적이 다르다. 총량 차단은 크레딧을 지키고, 서킷 브레이커는 **GMS 장애가 우리를 거쳐 Spring까지 번지는 것**을 막는다. 게이트웨이가 죽으면 매 요청이 30초를 기다리고 동시 요청이 열 개면 커넥션 열 개가 같이 물린다. 죽은 걸 아는데 계속 두드리는 게 문제다.

**이 구간에서는 하지 않는다.** `-127`의 완료 조건에 없다. 별도 티켓으로 세울지 `-127`을 넓힐지 정해야 한다. 넣게 되면 `DSLValidationError`는 실패로 세지 않는다 — 그건 우리 문제지 게이트웨이 문제가 아니고, 프롬프트가 나쁜 날에 멀쩡한 게이트웨이를 차단하게 된다.

**티켓 없이 떠 있는 것 하나 더.** `TranslateMeta.warnings`가 `app/services/translator.py:45`에서 `[]`로 하드코딩돼 있고 경고를 만드는 함수 자체가 없다. [DECISIONS.md](DECISIONS.md)의 "검증을 세 층으로 나눈다"가 경고 층을 정해 놨는데 통째로 비어 있다. **이 구간에서 하지 않는다** — S-1이 상한을 걷어내는 작업이라 경고 규칙을 같이 넣으면 두 성격이 한 커밋에 섞인다. 별도 티켓으로 뺀다.
