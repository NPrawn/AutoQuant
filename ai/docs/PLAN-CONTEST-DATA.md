# 대회 데이터 생성·검증 설계

- 상태: 검토 대기
- 날짜: 2026-09-14
- 결정 기록: [docs/adr](../../docs/adr/README.md) ADR-0001 ~ ADR-0013

## 1. 목표

연습 백테스트는 2018~2025 실제 데이터를 그대로 쓴다. 대회는 이 데이터를 조작해 누구도 백테스트해 본 적 없는 시장으로 채점한다.

이 문서는 세 가지를 설계한다.

1. 대회 시장을 만드는 생성기
2. 그 시장이 실제로 가능하고 안전한지 확인하는 검증
3. 로컬에서 대회를 한 번 돌려 보는 리허설

**완료 조건:** ADR-0012의 1~4단계를 통과하고, 대회 리허설 채점표가 상식 확인(10장 6번)을 통과한다. 그러면 ADR-0011을 채택으로 바꾼다.

## 2. 범위

| 이번에 만든다 | 만들지 않는다 |
|---|---|
| 생성기, 검증기, 채점기 (`ai/contest/`) | `contest` 스키마 migration, 대회용 `HistoricalCandleProvider` (백엔드, ADR-0006) |

## 4. 데이터

### 4.1 원본 (확보 대기)

1시간봉 CSV. 2018-01-01T00:00Z 이상, 2026-01-01T00:00Z 미만.

```sql
\copy (
  SELECT a.exchange_market_code AS market_code, c.asset_id, c.open_time,
         c.open_price, c.high_price, c.low_price, c.close_price,
         c.trade_volume, c.trade_amount
  FROM market_data.minute_candle c
  JOIN reference.asset a USING (asset_id)
  WHERE c.interval_minutes = 60
    AND c.open_time >= '2018-01-01T00:00:00Z'
    AND c.open_time <  '2026-01-01T00:00:00Z'
  ORDER BY a.exchange_market_code, c.open_time
) TO 'source_1h.csv' WITH CSV HEADER
```

종목 CSV는 `SELECT * FROM reference.asset WHERE exchange = 'UPBIT'`로 받는다.

2018~2025 데이터가 어느 DB에 있는지는 아직 확인하지 않았다 (ADR-0005).

### 4.2 대회 데이터

| 데이터셋 | 내용 |
|---|---|
| `GENERAL` | 일반장. 실제 전이 비율대로 주를 이음 |
| `BULL` / `BEAR` / `SIDEWAYS` | 평가 구간을 한 라벨의 주로만 채움 |

- 각 18주(워밍업 5 + 평가 13)다. 종목당 1시간봉 최대 3,024개, 4시간봉 756개, 일봉 126개다.
- 출력은 데이터셋마다 두 파일이다.
  - `candles.csv.gz`: `asset_id, interval_minutes, open_time, open_price, high_price, low_price, close_price, trade_volume, trade_amount`
  - `manifest.json`: `kind`, `seed`, `params`, `generator_version`, `source_sha256`, `weeks`(뽑은 주 시작일과 순서), `period_start`, `period_end`, `max_factor_period`(timeframe별 상한, ADR-0013), 간격별 행 수, `candles_sha256`

## 5. 생성 알고리즘 (ADR-0011)

### 5.1 파라미터

| 이름 | 기본값 | 의미 |
|---|---|---|
| `BLOCK_DAYS` | 7 | 블록 길이 |
| `BLOCK_START` | `MON` | 블록을 자르는 요일. `THU`와 4단계에서 비교 |
| `WARMUP_WEEKS` | 5 | 워밍업 주 수. 팩터 기간 상한을 함께 정한다 (ADR-0013) |
| `EVAL_WEEKS` | 13 | 평가 주 수 |
| `CANDIDATES` | 1,000 | 장세 후보 수 |
| `TARGET_BULL` | +20% ~ +30% | 평가 13주 universe 균등 보유 수익률 |
| `TARGET_BEAR` | -20% ~ -10% | 〃 |
| `TARGET_SIDEWAYS` | -3% ~ +3% | 〃 |
| `VOLUME_REF_WEEKS` | 4 | 거래량 수준을 맞출 기준 주 수 |
| `VIRTUAL_START` | 2030-01-07T00:00Z (월) | 생성 데이터의 첫 봉 시각. `BLOCK_START=THU`면 2030-01-03(목) |

### 5.2 절차

1. **블록 풀.** 원본을 `BLOCK_START` 요일 00:00 UTC부터 7일씩 자른다. universe 모든 종목이 그 주 시작 전에 첫 캔들이 있고 그 주가 끝난 뒤에도 캔들이 있는 주만 풀에 넣는다. 거래가 없어 비어 있는 시간은 원본 그대로 비워 둔다.
2. **라벨.** 주마다 universe 균등 보유 수익률(종목별 `주 마지막 종가 / 직전 봉 종가 − 1`의 평균)을 구한다. 풀 전체의 1/3, 2/3 분위수로 하락·횡보·상승을 나눈다. 실제로 이어진 두 주의 라벨 쌍을 세어 전이 행렬을 만든다.
3. **일반장.** 첫 주 라벨은 라벨 비율대로, 이후는 전이 행렬대로 뽑는다. 라벨이 정해지면 그 라벨의 주에서 하나를 고른다. 한 데이터셋 안에서 같은 주는 두 번 쓰지 않는다.
4. **장세.** 워밍업 5주는 일반장과 같은 방식으로, 평가 13주는 해당 라벨의 주에서 중복 없이 뽑는다. 이렇게 후보 1,000개를 만들어 목표 범위에 드는 후보 중 하나를 고른다. 범위에 드는 후보가 없으면 실패로 끝낸다.
5. **잇기.** 생성 데이터의 `i`번째 주, 종목 `m`마다 다음을 적용한다.
   - 가격 비율 `k = 생성 데이터 직전 봉 종가 / 원래 주 직전 봉 종가`. 첫 주는 `k = 1`이다.
   - 모든 가격에 `k`를 곱하고 호가 단위에 맞춘 뒤, `고가 = max(시가, 고가, 저가, 종가)`, `저가 = min(...)`으로 보정한다.
   - 거래량 비율 `v = 생성 데이터 직전 4주 1시간 거래량 중앙값 / 원래 주 직전 4주 1시간 거래량 중앙값`. 생성 데이터가 4주가 안 되면 있는 만큼 쓰고, 첫 주는 `v = 1`이다.
   - 거래량에 `v`, 거래대금에 `k × v`를 곱한다. 그러면 `거래대금 ÷ 거래량`(평균 체결가)이 가격과 같은 비율로 움직여 저가~고가 안에 남는다.
   - 호가 단위는 원본에서 가격대(10의 거듭제곱 구간)별로 관측한 가장 작은 가격 차이로 표를 만든다.
6. **시각.** `i`번째 주의 봉 시각은 `VIRTUAL_START + i주 + (원래 봉 시각 − 원래 주 시작)`이다. 요일과 시간대가 원래 주와 같다.
7. **집계.** 4시간봉과 일봉은 생성한 1시간봉을 UTC 기준으로 잘라 집계한다 (ADR-0005).
8. **기록.** manifest를 쓰고 두 파일의 sha256을 남긴다.

### 5.3 결정성

- 난수는 `random.Random(seed)` 하나만 쓰고 호출 순서를 고정한다.
- 원본 sha256, 시드, 파라미터, 생성기 버전이 같으면 `candles_sha256`이 같아야 한다. 테스트로 막는다.

## 6. 검증 (ADR-0012)

### 6.1 실제 비교 기준

블록 풀에서 실제로 이어진 18주를 한 주씩 밀어 실제 구간을 만든다 (최대 약 400개). 1·2단계 통계는 전부 쓰고, 엔진 실험은 무작위 20개를 쓴다.

### 6.2 단계

| 단계 | 필요한 것 | 통과 기준 요약 |
|---|---|---|
| 1. 가능한가 | 원본 | 라벨마다 30주 이상, 라벨이 한쪽으로 쏠리지 않음, 장세 후보가 목표 범위에 도달 |
| 2. 값이 진짜 같은가 | 원본 | 봉 검사 위반 0건, 이음매 분포가 일반 시점과 구분되지 않음, 긴 흐름 통계가 실제 구간 분포 안 |
| 3. 외워 맞추기가 막히는가 | 엔진 | 과적합 전략의 성적 하락이 견고한 전략보다 뚜렷하게 큼 |
| 4. 공정한가 | 엔진 | 유형별 순위 차이, 시드 간 순위 상관, 이음매 요일 차이가 실제 구간끼리의 차이 범위 안. 같은 시드면 해시 일치 |

세부 기준과 실패 시 조정은 ADR-0012에 있다.

### 6.3 universe (1단계에서 확정)

| 후보 | 기대 | 걱정 |
|---|---|---|
| 2018년 이전 상장, 2025년 말까지 거래 중인 종목 중 거래대금 상위 30 | 블록 풀이 가장 큼 | 요즘 종목이 빠짐 |
| 2025년 거래대금 상위 30 | 요즘 시장과 비슷함 | 블록 풀이 2024~2025년 위주 |
| 서비스 수집 대상 (`market_data.market_data_collection_target`) | 서비스 화면과 일치 | 블록 풀 크기 미지수 |

라벨마다 30주 이상을 채우는 후보 중에서 서비스 종목 구성과 가장 가까운 것을 고른다.

### 6.4 전략 세트 (3·4단계, 32개)

| 묶음 | 수 | 만드는 방법 |
|---|---|---|
| 유형별 기본 | 20 | 추세추종(RETURN 상위), 평균회귀(RSI 낮은 순), 저변동성(VOLATILITY 낮은 순), 거래량(VOLUME_RATIO 상위), 추세 필터(SMA_DISPARITY > 0) × timeframe·기간 변형 4개씩 |
| 과적합 | 5 | 실제 8년 1D 데이터에서 기간(2~34), 기준값, 상위 N, 리밸런싱 조합 약 300개를 엔진으로 돌려 수익률 상위 5개 |
| 견고 | 5 | 같은 300개 중 기간 ±20% 이웃 조합과 성적 차이가 가장 작은 5개 |
| 규칙 확인 | 2 | 현금 대기(통과하지 못하는 필터), 1종목 몰빵(상위 1개) |

모든 전략의 팩터 기간은 상한(1H 839, 4H 209, 1D 34, ADR-0013) 안에서 잡는다.

### 6.5 엔진 규모

1. 18주 × 30종목 데이터로 1H·4H·1D 백테스트를 한 번씩 돌려 시간을 잰다.
2. 기본 규모는 전략 32개 × (생성 시장 20벌 + 실제 구간 20개) = 1,280회다.
3. 너무 느리면 1H 전략을 줄이고 4H·1D 위주로 바꾼다.

### 6.6 리포트

단계마다 `ai/docs/contest-validation/stage-N.md`(판정)와 같은 이름의 CSV(수치)를 남긴다. 결과는 ADR-0012에 기록한다.

## 7. 채점 (ADR-0002, ADR-0003)

```
수익률 점수 = GENERAL 누적수익률의 백분위
안정성 점수 = 0.6 × 평균(BULL, BEAR, SIDEWAYS 각각의 MDD 백분위) + 0.4 × 최저(같은 셋)
총점       = w × 수익률 점수 + (1 − w) × 안정성 점수
백분위     = (n − 순위) / (n − 1) × 100   # 순위 1 = 가장 좋은 성적 (수익률은 높을수록, MDD는 낮을수록)
                                          # 실격자 제외, 동점은 평균 순위
```

- **실격:** 4개 데이터셋 중 하나라도 수익률 -30% 미만이거나 MDD 50% 초과면 실격이다. `GENERAL`의 평균 투자 비중이 하한보다 낮아도 실격이다.
- **평균 투자 비중:** 평가 구간 equity의 `1 − 현금 / 총자산` 평균이다.
- **기본값:** `w = 0.5`, 투자 비중 하한 30%. 리허설 뒤 조정한다.

## 8. 로컬 시뮬레이션 환경 (ADR-0007)

- **인프라.** `infra/docker-compose.yml`로 Postgres·RabbitMQ·Redis를 띄우고, develop 기준 Spring을 로컬에서 기동한다. 스키마는 Flyway가 만든다.
- **Spring 설정.** `JWT_SECRET`(32바이트 이상)을 정하고, 비어 있으면 기동되지 않는 SSAFY OAuth 설정에는 더미 값을 넣는다. 이 값들은 Spring 프로세스의 로컬 환경변수다.
- **실행기 설정.** `ai/CLAUDE.md`는 `os.environ`을 `app/core/config.py`에서만 읽게 한다. 실행기는 환경변수를 읽지 않고, 명령행 인자와 커밋하지 않는 로컬 JSON 설정 파일(API 주소, DB 컨테이너 이름, 토큰 비밀값)로 받는다.
- **인증.** `account.member`에 행 하나를 넣는다. HS256 JWT(발급자 `a107`, subject에 member UUID, 만료 시각)를 표준 라이브러리(`hmac`, `hashlib`, `base64`)로 만들어 `Authorization: Bearer` 헤더로 보낸다.
- **종목.** universe 종목을 `reference.asset`에 넣는다. `trading_support_started_at`과 `trading_support_ended_at`은 비워 둔다. 엔진의 종목 조회는 두 값이 비어 있으면 기간과 무관하게 후보로 본다.
- **적재.** 데이터셋마다 `market_data.minute_candle`을 비우고 `docker compose exec`로 `psql \copy`를 실행해 1H·4H·1D를 넣는다. 롤업 트리거는 1분봉 insert에만 걸려 있어 동작하지 않는다.
- **실행.**
  - `POST /strategies`: DSL은 `app/core/schema.py` 모델로 만들고 검증한다. 팩터 기간이 상한을 넘으면 실행기가 제출 전에 거부한다 (운영의 제출 검증을 대신함).
  - `POST /backtests`: 기간은 평가 13주(`VIRTUAL_START + 5주`부터), `marketDataVersion`은 데이터셋 이름과 시드, `engineVersion`은 `local-sim`, 초기 자본 1,000만 원, 수수료 0.0005, 슬리피지 10bps, `NEXT_CANDLE_OPEN`
  - 완료될 때까지 폴링하고 `result`와 `equity`를 받는다.
- **결과.** (데이터셋, 전략)마다 상태, 누적수익률, MDD, 평균 투자 비중, 거래 수를 CSV로 모은다.

```
  run.py             # 백테스트 제출, 폴링, 결과 수집
  experiments.py     # 3·4단계 실험, 대회 리허설
ai/tests/
  test_contest_blocks.py      # 블록 풀, 라벨, 전이 행렬
  test_contest_generate.py    # 결정성, 잇기, 호가 단위, 집계 일치
  test_contest_checks.py      # 봉 검사가 위반을 잡는지
  test_contest_scoring.py     # 백분위, 동점, 실격, 총점
```

- `ai/contest/`는 표준 라이브러리만 쓰고 `app/`을 임포트하지 않는다. AI 서버와 분리하기 위해서다.
- `ai/scripts/contest_sim/strategies.py`만 `app/core/schema.py`를 쓴다. `schema.py`는 표준 라이브러리와 pydantic만 임포트해서 LLM 설정 없이 불러올 수 있다.
- 테스트는 기존 `ai/tests/` 평면 구조를 따른다. 작은 가짜 원본(종목 3개, 몇 주)을 테스트 안에서 만들어 쓴다.

## 12. 미결 사항

1. **원본 위치.** 2018~2025 데이터가 있는 DB를 확인해야 한다.
2. **`w`와 투자 비중 하한.** 리허설 뒤에 정한다.
3. **블록 자르는 요일.** 4단계에서 정한다.
4. **가상 날짜.** 2030년 시각을 쓸 때 백엔드 검증에 걸리는 곳이 없는지 로컬에서 확인한다. 백테스트 요청 DTO와 `trading.backtest_run` 제약에는 미래 날짜를 막는 규칙이 없다.
5. **화면 설계.** `30-대회 목록`, `31-대회 상세`의 연습용 장세 영역을 고치고, 팩터 기간 상한을 보여 달라고 요청한다.
6. **백엔드 요청.** ADR-0006의 migration, 대회용 provider, 캔들 변환 팩토리와 ADR-0013의 제출 시 팩터 기간 검증.

## 13. 대회 규칙 문구 (초안)

> 채점 데이터는 실제 과거의 한 주들을 뽑아 새 순서로 이어 붙인 시장입니다. 한 주 안의 움직임은 실제 그대로이고, 상승 주 다음에 상승 주가 오는 비율 같은 흐름은 실제 과거를 따릅니다. 상승장은 실제 상승 주들만 모은 것입니다. 채점 데이터는 마감 후 공개합니다.
>
> 대회 데이터에는 평가 시작 전 35일치만 제공합니다. 지표 기간은 1시간봉 839, 4시간봉 209, 일봉 34까지 쓸 수 있고, 이보다 긴 기간을 쓴 전략은 제출할 수 없습니다.
